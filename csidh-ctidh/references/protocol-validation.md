# Public-key validation and protocol integration

## Typed boundary

Keep separate representations:

```text
EncodedPublicKey
  -> decode(parameterSet)
DecodedCurve
  -> validate(parameterSet)
ValidatedPublicKey
  -> secretAction(SecretExponent)
SharedCurve
  -> canonicalEncode + transcript KDF
SessionKey
```

Make it impossible for the secret-action API to accept `EncodedPublicKey` or unvalidated `DecodedCurve`. Carry the exact construction/parameter identifier in the type or owning context.

## Canonical decoding

For a Montgomery-coefficient public key, enforce the exact selected encoding:

- Fixed length.
- Defined byte order.
- Canonical field element range; reject alternate encodings of the same value.
- Correct curve model/equation for the parameter set.
- Nonsingularity.
- No trailing bytes or implicit parameter inference.

Do not normalize an invalid/noncanonical value and continue. Preserve original bytes for transcript binding only after canonical acceptance.

## Full validation

Range and discriminant/nonsingularity checks do not establish membership in the expected CSIDH action set. Use the exact selected algorithm to establish the required supersingularity/class/order property before applying a secret action.

Validation requirements are construction- and parameter-specific. Record:

- Mathematical property checked.
- Algorithm/citation/source revision.
- Probabilistic versus deterministic behavior and error probability.
- Work/timeout bound.
- Randomness, if any.
- Failure result and cleanup.

Run validation on every untrusted public key, including cached/restored keys unless their authenticated storage and parameter identity are proven. Never use “generated by this library” as a network trust condition.

## Invalid-key behavior

Reject before secret action:

- Wrong length/endianness/noncanonical field encoding.
- Singular or unsupported curve.
- Ordinary/wrong-class/non-supersingular key.
- Different CSIDH/CTIDH/dCTIDH parameter set.
- Identity/base-curve values prohibited by the containing protocol.
- Unsupported version/construction identifier.

Keep externally visible failure behavior from becoming a secret-action oracle. Bound validation work and rate-limit adversarial peers.

## NIKE and KDF

A shared curve coefficient is structured pre-key material, not a symmetric key. Define:

```text
IKM  = canonical(sharedCurve)
info = encode(
  protocolVersion,
  ciphersuite,
  constructionAndParameterId,
  roleA, canonical(publicKeyA),
  roleB, canonical(publicKeyB),
  transcriptHash,
  applicationContext
)
keyMaterial = KDF(salt, IKM, info)
```

Use a reviewed KDF with explicit output partitioning. Define canonical public-key ordering independent of local “self/peer” views, then include roles so both participants derive the same material without reflection ambiguity.

## Protocol properties

State separately:

- Peer authentication method.
- Key confirmation.
- Replay/session uniqueness.
- Forward secrecy and secret-key lifetime.
- Identity protection.
- Downgrade prevention.
- Hybrid combiner and failure policy.
- Public-key reuse/static-key policy.

Commutativity supplies non-interactive agreement, not authentication, confirmation, transcript binding, or forward secrecy.

## Hybrid composition

If combined with another KEM/DH primitive:

1. Bind both algorithm identifiers, parameters, public/ciphertext inputs, and outputs in one reviewed combiner/KDF.
2. Define failure behavior without revealing which component failed where that matters.
3. Preserve security when either component output is malformed, repeated, or attacker-controlled according to the combiner proof.
4. Version the complete hybrid suite; never negotiate components independently without downgrade protection.

## Secret lifecycle

Protect exponent vectors, random sampling state, action intermediates, shared curves before KDF, and derived keys. Define zeroization, object reuse, concurrency, process fork/snapshot, crash dumps, and hardware export policy. Long-lived static NIKE secrets require stronger compromise and rotation analysis than ephemeral exchanges.
