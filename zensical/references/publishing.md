# Publishing and offline output

## Build an artifact, not a preview service

1. SET the canonical site_url to the exact published location, including a repository prefix such as `https://example.github.io/project/`. Verify canonical tags, sitemap entries, deep-page relative links and assets against that prefix.
2. RUN the project's pinned environment: `uv sync --locked` then `uv run zensical build --clean --strict`, or install its declared pinned pip requirements and invoke that environment's executable. Run required content generators first.
3. PUBLISH only the configured site_dir. Use GitHub Pages, GitLab Pages, a CDN or dedicated static web server with routing compatible with use_directory_urls. `zensical serve` and the official Docker image's preview command are not production servers.
4. TREAT strict build as an internal-link gate, not proof of external-link availability, plugin preservation, secrecy or accessibility. Verify rendered behavior and publication exclusions separately.
5. AVOID carrying Zensical's build cache across CI runs while upstream caching is evolving; use --clean per current publishing guidance. Package-manager dependency caches are a separate policy. Never deploy preview output containing drafts.

Sources: [publishing](https://zensical.org/docs/publish-your-site/), [build](https://zensical.org/docs/usage/build/), [preview-only server](https://zensical.org/docs/usage/preview/).

## Integrate GitHub Pages

1. INSPECT the workflow generated by `zensical new`: it is deployment configuration, not harmless sample content. Merge into the actual CI owner; preserve branch/environment protections and avoid introducing automatic publishing unless requested.
2. CONFIGURE the repository's Pages source for GitHub Actions only with authorized account/repository-setting changes. Use the actual deploy branch, not both main/master by habit.
3. BUILD with contents:read permissions; upload site_dir through upload-pages-artifact. Limit pages:write and id-token:write to the approved deployment job/environment; use configure-pages and deploy-pages per current official docs. Pin actions to verified revisions using the repository's policy and select an explicit supported Python/Zensical version or lockfile.
4. For PRs, run build/validation without deployment permissions. Do not combine privileged tokens with execution of untrusted Markdown macros, custom Python handlers or execution fences.
5. VERIFY the actual deployed URL and deep links only after authorized publishing. If only preparing a workflow, report it as configured but unexecuted; no gh-deploy command exists in Zensical.

Source: [GitHub Pages workflow and prerequisite](https://zensical.org/docs/publish-your-site/#github-pages), [GitHub Pages source configuration](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site#publishing-with-a-custom-github-actions-workflow).

## GitLab and other static hosts

USE the provider's supported artifact publishing configuration, set it to the actual site_dir, restrict deployment to the protected/default branch, and verify its hostname/path prefix and access policy. GitLab can publish site directly through pages.publish instead of moving it to public. Do not change site visibility or unique-domain settings merely because an example suggests them; select the user-approved target.

Source: [GitLab Pages](https://zensical.org/docs/publish-your-site/#gitlab-pages).

## Offline file distribution

1. ENABLE `[project.plugins.offline]` (YAML plugins: offline). This adjusts directory URLs and search for file-system access; it does not make every network dependency local.
2. DISABLE instant navigation and other fetch-dependent analytics/repository/comment integrations for an actual offline package. Include required fonts, JS/CSS and images locally under the approved dependency policy.
3. INCLUDE the iframe-worker shim locally through project.extra.polyfills if network-independent file:// search is required; its filename must contain iframe-worker or the runtime fetches it from unpkg.com. Do not claim offline readiness from HTTP preview alone.
4. BUILD and open the generated files through file:// on the target browser with network unavailable; exercise search and deep links. Network-disabled HTTP preview and package installation are different tests.

Source: [offline configuration and shim caveat](https://zensical.org/docs/setup/offline/).
